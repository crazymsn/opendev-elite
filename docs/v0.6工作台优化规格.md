# OpenDev Elite v0.6 · 工作台审核与双语优化

目标：围绕用户给定的完整开发者赞助 SOP，优化逻辑架构、前端 UI/排版、入选标准和中英双语仓库档案。v0.6.0 已于 2026-09-07 完成软件交付及本机升级，SQLite schema 6。结果与边界见 [交付说明](v0.6交付说明.md)及 [验收矩阵](v0.6验收矩阵.md)。

## 开始实施时的审核发现（v0.5.1 基线）

- 本机 SQLite 有 145 个候选项目，公开描述以英文为主。检索命中存在广义 AI 关键词项目，不能把搜索命中当作入选。
- `workflow.py` 已实施当前 SHA、30 天证据有效期、两轮通过后联系、真实人/Agent 体验、访谈、独立审批与发放。上述约束应继续集中在服务端。
- 第一轮现有 structure/maintenance/documentation 三项证据，但缺少独立的方向适配、维护状态和入选结论；页面无法明确展示候选与入选的区别。
- 仓库详情把英文描述、README 与原始 JSON 放在同一纵向区域。缺少中文档案、翻译状态和清晰的原文核对入口。
- 界面文案散落在 app.js、forms.js、accounts.js、landing.js 和服务端待办中，需要统一双语词典和明确的文本边界，避免翻译代码、账号、URL 和用户证据。

## 必须交付与验证

1. **规范入选标准**：候选发现不自动入选。持续维护的 AI 开发者工具、Agent 基础设施及相关应用为范围；个人、小团队和早期项目均可，不按国籍、地域、Stars、融资或团队规模淘汰。方向适配和维护判断须有来源、理由、当前 SHA 和责任人；不确定可暂缓。
2. **完整 SOP 门槛**：方向/维护确认 → 三项技术复核 → 人/Agent 实际体验与产品复核 → 联系 → 访谈及画像 → 赞助审批 → 独立 Credits 执行与到账核对 → 到期复盘。页面“下一步”和 API/CLI 应来自同一规则。证据更新、换 SHA、重新评估要使旧结论失效，历史事实保留。
3. **工作台 UI**：概览突出可执行待办；候选列表支持有效筛选/搜索并清楚区分当前状态；详情以仓库档案、入选评估、技术复核、体验、建联/访谈、赞助/复盘分区。减少原始 JSON 在主流程中的干扰。统一间距、文字、表单、状态、空态、错误和响应式布局。
4. **中英双语**：可切换、记住语言，覆盖导航、概览、列表、详情、表单、账号管理、待办与常见错误。项目名、代码、原始证据和用户输入不被界面翻译器改写。
5. **中文仓库档案**：中文/英文阅读，保留原文、来源及翻译更新时间；翻译绑定源内容摘要，源文变化后标记失效。中文简介、README 阅读/摘要有明确状态，不能把未翻译英文或模板文字标成中文译文。为后续采集提供可重复的翻译导入/更新通道，已有项目需要实际中文内容验证。
6. **部署与迁移**：保持默认 OpenDev / 123456 及管理员后台创建成员的既有要求；`docker compose up -d` 保持可用。升级先备份，保留旧账号与业务数据。
7. **验收**：针对新规则的正反例与全量回归；真实浏览器中英两种语言下走完整关键路径；375/768/1024/1440 宽度、键盘与无溢出检查；安装包/静态资源验证；本机升级后验证。没有 Docker Engine 时如实记录，不能声称容器实机通过。

## 实施顺序

1. 集中入选标准、持久化评估与资料翻译模型，补充流程门槛与回归。
2. 集中项目查询/档案/准备状态，前端消费同一事实，支持分类、维护、阶段、入选状态筛选。
3. 实施双语基础设施，重构概览、候选和仓库详情，统一表单和账户页面。
4. 完成实际档案中文翻译和来源绑定，并验证更新后不会显示过期译文。
5. 浏览器、完整测试、发布包、迁移备份和线上升级，逐项审计要求再关闭目标。

## 设计约定

沿用暖白与深绿品牌色，正文提高可读性；侧栏按项目评估、赞助运营、系统管理分组。8px 基础间距，紧凑元数据与宽松阅读区分开；表单按决策顺序分组，主要动作每个区域一个。桌面详情采用主内容与评估摘要两列，窄屏单列；双语文案预留更长英文布局。真实数据和合成验收数据继续分离。
