# GitHub 采集身份配置

GitHub 采集身份与 OpenDev Elite 登录账号不同：前者用于读取仓库 API，后者控制团队工作台权限。没有 GitHub 身份仍可低速读取公开数据，但可能因匿名配额导致采集长时间等待。不能由页面“已连接”推断 GitHub 已经认证。

## 本机复用已有 GitHub CLI 登录

0.7.3 起，本地部署可读取运行目录中的 `github.local.json`：

```json
{
  "credential_source": "github-cli"
}
```

确认运行服务的同一操作系统用户已安装 gh，并已通过 `gh auth login --hostname github.com` 登录。将示例 `config/github-auth.example.json` 复制为运行目录中的 `github.local.json` 后，停止并重新启动本地服务。不要把它放到源码目录冒充运行配置。

本地 API 和采集 Worker 启动时调用固定的 `gh auth token --hostname github.com`，把返回令牌保留在自身进程内存中。配置文件不保存令牌，不接受额外命令或参数；日志只报告身份来源和是否配置。退出进程后不再保留这份内存副本。GitHub CLI 自己的登录凭据仍由 gh 管理。

选用 gh 后，如果程序不可用、未登录或凭据格式无效，启动明确失败，不会悄悄退回匿名请求。没有这个配置文件时，不会自动读取 GitHub CLI 登录。

## 显式环境变量和文件

本地启动优先使用非空 `GITHUB_TOKEN`，其次读取 `GITHUB_TOKEN_FILE` 指向的私有令牌文件，最后才考虑上述 gh 配置。文件最多 16 KiB，内容必须是单行 ASCII 令牌；读取失败会明确报错。不要在命令行参数、文档、聊天或截图中粘贴真实令牌。

Docker 继续沿用既有环境变量和 Secret 文件入口，不要求安装 gh。容器入口仍拒绝同时指定 `GITHUB_TOKEN` 与 `GITHUB_TOKEN_FILE`，避免配置歧义。若挂载的数据卷里有本机 gh 配置而容器没有 gh，应提供容器的令牌配置或在迁移前移除该本机选项。

## 如何验证

1. 查看本地 `logs/run.log` 的 `GitHub authentication source=... configured=...` 启动记录。身份已配置本身不证明令牌有效；工作台“采集与运行”展示队列任务，不能代替此项身份检查。
2. 查看真实采集任务是否完成、快照日期是否推进；以实际 GitHub 响应的配额与状态核对认证生效。
3. 区分身份失败、限流、网络错误和项目数据缺失。更换身份不改变候选、审核、体验或赞助记录。

旧限流已写入队列等待时间时，身份切换不会自动清除所有重试等待。只有验证新身份的实际可用配额后，才可评估是否恢复相关采集任务；不能把网络错误或其他等待一并当作可忽略。

本次仅为 GitHub 只读采集接入身份，不增加消息发送、仓库写入或 Credits 权限。

## 公开仓库范围

无论是否认证，发现查询均限定 `is:public`；显式私有或内部仓库查询会在入队前拒绝，双引号内的普通检索文字保持原样。[GitHub 官方搜索说明](https://docs.github.com/en/search-github/searching-on-github/searching-for-repositories)明确区分公开仓库与账号可访问的私有仓库。

搜索返回后，只导入有公开可见性依据的条目，异常条目计入 `filtered_visibility_items`，该页覆盖标记为不完整。`fetched` 记录原始返回数量，`accepted_public_items` 记录实际接受数量。刷新时先读取仓库元数据；私有、内部、未知或矛盾的可见性会停止后续代码和作者资料请求，不写项目快照。这些是采集范围约束，不是项目入选或排除结论。

该判断依据 GitHub 在请求时返回的元数据；不能保证仓库今后的可见性不变。令牌权限没有被程序修改，应通过 gh 或 GitHub 管理实际授权。

## 回滚旧运行环境

回滚到 0.7.2 时，先停止当前服务，把 `github.local.json` 移到运行目录的备份子目录，再启动旧版本。0.7.2 的目录检查不识别该新文件；只切换 Python 路径会导致初始化拒绝启动。保留这份无令牌配置，重新升级后可以恢复。旧版仍需使用其支持的环境变量方式接入 GitHub 身份。
