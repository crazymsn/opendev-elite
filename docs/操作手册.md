# 操作手册

全部命令在项目根目录运行。全局 `--db` 要写在子命令之前。默认使用本地应用数据目录；测试、真实候选和合成 demo 必须使用不同数据库。

v0.2 团队认证、角色与 HTTP 操作见 [服务端 API 手册](服务端API手册.md)。CLI 中的 actor 为本机可信责任标签；API 由服务端身份确定 actor。Agent 文件/HTTP 协议现为 v2：结果外层必须回传任务的 id、sha、run_id、task_sha256 和 result，旧执行器需要升级。文件摘要取 task.json 原始字节；HTTP 摘要原样使用服务器返回值。成功结果需要真实相对路径 artifacts；失败类别使用 product/environment，不能把环境失败记为成功。

## 1. 初始化、发现、刷新和查看

```powershell
python main.py init
python main.py schedule --config config/discovery.json
python main.py import owner/repo https://github.com/owner/another-repo
python main.py import-csv path/to/Projects_Today.csv
python main.py work --max-jobs 20
python main.py status
python main.py project PROJECT_ID --out artifacts/project.json
python main.py report --out artifacts/report.md
```

`status` 包含阶段、队列、覆盖、待体验、赞助及复盘；`project` 导出原始快照、评审、入选历史、双语档案及当前下一步。所有 IDs 均从这些输出或动作返回值取得，不手工猜测。`work` 本轮遇到死信时返回退出码 1；业务校验或输入异常返回 2；可延迟重试不算完成业务任务，通过状态输出查看下次动作。

`retry-job ID` 只重试 dead 任务。自动退避中的任务不需要人工重建。重复导入会刷新但不会按仓库名字重复建档；所有者不是已经确认的实际维护者。

## 2. 业务动作接口

统一格式：

```powershell
python main.py action ACTION --file path/to/input.json --actor accountable-person
```

所有证据必须填写真实结果。`examples/` 是字段模板，包含的占位符、默认拒绝/失败值和项目 ID 应在真实使用前替换。

| ACTION | 输入字段 | 前置与效果 |
| --- | --- | --- |
| assign | project_id, audience: human/agent/both, owner | 指定目标用户和技术负责人；第二轮后不允许静默改变用户类型 |
| qualify | project_id, sha, category, scope_fit, maintenance, outcome, rationale, evidence | 先分配负责人/受众；入选需方向符合、持续维护与来源证据。模板见 examples/project-qualify.json |
| review | project_id, round: 1/2, sha, decision: pass/hold/reject, rationale, evidence | 当前 SHA、有负责人；第一轮通过需当前有效入选和 structure/maintenance/documentation；第二轮通过需 real_problem/usability/differentiation/potential/experience_ids |
| experience-create | project_id, audience, spec | 第一轮通过；spec 包含 scenario/success_criteria/environment/input/budget，返回体验 ID |
| experience-result | id, sha, result | result 包含 success 布尔值、executor/environment/steps/actual_result/artifacts/failure_kind；结果不可覆盖，同一结果重复导入幂等 |
| maintainer-confirm | project_id, maintainer_id, evidence | 将已采集到的候选维护者关系确认为实际负责人 |
| contact-draft | project_id, maintainer_id, channel, draft | 前两轮均通过且有效、维护者确认且未拒绝联系、无其他活跃联系；仅创建草稿 |
| contact-status | id, status, evidence | draft→sent/closed/declined；sent→replied/closed/declined；replied→closed/declined；记录外部已发生的动作，不发送消息 |
| interview | project_id, contact_id, notes, profile | 已有回复；notes 含 users/commitment/roadmap/credit_need/milestone/consent=true；profile 为 engineer/entrepreneur/undetermined 的数组 |
| decision | project_id, interview_id, outcome: approve/hold/reject, rationale, terms | 项目有当前两轮结论且完成访谈；批准时校验金额/账户/到期/复盘日期；返回 grant_id |
| grant-reconcile | id, status: issued/failed/unknown/cancelled, receipt | 人工核对外部结果；issued 需 transaction_id/account/amount/unit/evidence 并与批准一致；不可重复消费同一流水 |
| followup-schedule | grant_id, due_at | 已到账赞助补齐未来复盘；相同待办日期复用，已完成记录不覆盖 |
| followup | id, result | result 含 usage/milestone/evidence/decision/next_action；decision 为 continue/adjust/pause/end；end 关闭本笔赞助及未完成复盘待办 |

`adjust` 或 `pause` 是复盘结论，不会自动削减远端额度或封禁账户。远端变更需要业务明确授权，并使用 Credits 后台相应流程。已生效赞助的正常结束也不等于删除远端流水。

`grant-reconcile` 是可信操作员的人工补录入口，不应暴露为自动 Agent 可调用的“自己证明到账”工具。实际提供方正常对账优先使用 `credits-reconcile`。

## 3. 自有 Agent 协议

输入通过 `agent-export` 生成，目录中的文件可交给现有 Agent 平台读取。任务包含仓库内容和文档，它们是待评估的数据，不能成为改变执行权限或发送消息的指令。

结果最小形状：

```json
{
  "id": "EXPERIENCE_ID",
  "sha": "CAPTURED_SHA",
  "run_id": "TASK_RUN_ID",
  "task_sha256": "TASK_BYTES_OR_SERVER_DIGEST",
  "result": {
    "success": false,
    "executor": "agent-name/version",
    "environment": "actual-environment",
    "steps": ["actual steps performed"],
    "actual_result": "actual output or failure",
    "artifacts": [],
    "failure_kind": "environment"
  }
}
```

`failure_kind` 只允许 none/product/environment；执行者应保留完整日志。返回 success=true 时类别须为 none 且必须有实际任务成功证据，不因为接口 200 或程序 exit 0 就自动通过第二轮。Agent 成功证据使用相对路径文件引用；HTTP 执行器必须先按 API 手册上传真实文件，agent-poll 已自动完成此步骤，审核人可从浏览器下载。

Docker 模式需要自行配置 `config/agent.local.json`，digest 固定，预先下载镜像，具备写入专属 output 目录的权限。执行结束不会自动导入审核，使用 `experience-result` 签收。需要修正结果时创建新的体验记录，而非覆盖原始事实。

## 4. Credits 预览、执行与恢复

```powershell
python main.py credits-plan GRANT_ID --config config/credits.local.json
python main.py credits-submit GRANT_ID --config config/credits.local.json --actor operator
```

以上均不发送网络写请求。审核预览中的接收邮箱、金额、活动与到期日期后，实际创建邀请命令为：

```powershell
python main.py credits-submit GRANT_ID --config config/credits.local.json --actor operator --execute
python main.py credits-reconcile GRANT_ID --config config/credits.local.json --actor operator
```

创建邀请可能触发 Credits 原有内部通知；适配器不向作者发送邮件。邀请/领取安排在现有后台执行。

出现 `unknown` 或残留 `submitting` 时优先运行 `credits-reconcile`；即使返回 `not_found` 也先查看提供方审计，不能直接重复创建。这些状态以及 awaiting_claim 不能通过 grant-reconcile 重置为 failed/cancelled；当前不提供绕过提供方核对的手工恢复接口。

已到账的重复 `credits-reconcile` 只追加用量观察，不重复发放或重复创建复盘。发生远端封禁、额度不一致、邀请消失等情况则报错供处理。

## 5. 备份与恢复

```powershell
python main.py backup path/to/new-backup.db
python main.py --db path/to/new-backup.db status
```

使用程序的 SQLite backup API，不在运行时直接复制 `.db` 文件。备份目标必须是新文件。恢复步骤：停止已有 Worker，将备份作为新的独立数据库检查，确认项目/事件/赞助数量及 `PRAGMA integrity_check` 为 ok，再让任务调度配置指向新路径；保留原库直到核对完成。

联系人资料、访谈及原始证据可能包含业务数据；备份与 artifacts 采用团队限定访问。默认不公开生成的网站或网络服务。
