## 接口和兼容变化

- `build_task(store, experience_id)`：读库、验证当前体验资格并构造 schema v2 任务；每次产生新的 run_id，因此服务端必须保存已发出的任务，不能收到结果后重新构造。
- `export_task(store, experience_id, destination)`：独占创建任务文件，返回 path、sha256、run_id、schema_version。
- `validate_result(task, data, artifact_root=None, task_sha256=None)`：校验身份绑定、结果结构和证据路径。文件执行模式传入输出目录和任务摘要；HTTP 模式不读取 Agent 声明的宿主文件路径，远程证据的实际获取和评审仍是独立流程。
- `run_agent(...)`：返回经过校验的结果，不自动完成体验、不自动通过第二轮，也不产生联系或赞助操作。

结果外层需要包含 `id`、`sha`、`run_id`、`task_sha256` 和 `result`。文件协议的 task_sha256 是 `task.json` 原始字节摘要；HTTP 协议按服务端返回的 task_sha256 原样回传。旧版只输出 id/sha/result 的执行器需要升级。

失败类别固定为 `none`、`product`、`environment`。成功必须对应 none；失败必须对应 product 或 environment。成功的 artifacts 为输出目录下相对路径字符串数组，例如 `evidence/output.txt`，不能使用 URL 或 `fixture:` 占位符。

## 部署前仍需完成的边界

1. Docker 的离线执行保持 `network=none`。当前任务携带仓库 URL、SHA 和证据快照，并不自动克隆源码、安装依赖或调用在线模型。执行镜像必须预装对应 SHA 的源码/依赖，或由独立受控准备步骤提供经审查的输入；缺少环境必须报告 environment failure。
2. 输出使用专用 bind mount。8 MiB 日志限制、1 MiB 结果限制和 64 MiB 被引用证据上限，不能替代操作系统对整个输出卷的硬配额。生产必须使用独立 runner 和带总容量配额的输出卷，才能阻止不被引用的大量文件填满磁盘。
3. nonce、SHA 和摘要验证的是结果归属，不能证明执行器诚实。第二轮仍需负责人员核对真实输出；HTTP 模式的远程证据也不能仅凭路径字符串认定真实。
4. 运行时限制不等于可安全运行任意第三方镜像。镜像须审核并按 digest 固定，宿主应是可销毁的专用执行节点；禁止在含生产凭据/共享敏感挂载的宿主上运行。
5. 未做真实 Agent/Docker/生产 Credits 联调，未对外发信，也未发放真实 Credits。

## 对其他模块的独立检查

报表问题已由本质控任务追加修复，CLI/数据库问题提交主任务整合：

- `report.summary` 的 ready_for_contact 现仅列出 ready_contact 阶段、当前两轮合格、无活跃联系且尚无业务决定的项目；已审批、hold/reject 或已结束联系后进入后续流程的项目不再重新进入候选。测试复现了“第三轮拒绝后再次签署二轮会把 stage 写回 ready_contact”的真实路径，并验证报表仍会排除它。已作决定的周期不会通过再次签署二轮自动重开。
- pending_experiences 现仅包含当前可执行的待体验；旧 SHA/过期/重审前创建/缺少完整快照的任务列入新增的 stale_experiences，并附原因。保留原有 summary 键，不修改体验原始状态，覆盖人与 Agent 两类体验。导出报告同步展示两组待办。
- 原 CLI 在 try 之前打开 Store，数据库迁移/权限/锁错误不能统一形成结构化 CLI 错误；init 曾硬编码 schema_version=1，需要取实际版本。
- SQLite 事务和租约令牌能支持本地受控流程，但账户标识字符串本身不是身份认证。多人服务的认证、角色权限、幂等和 Agent 租约由主任务实施，并需独立接口级测试。

本报告的结论是：已对上述本地执行边界完成有证据的修复；生产运行能力仍以环境联调和部署验收为准。
