# 外部集成与真实业务上线验收清单

此清单沿用 v0.3 引入的外部验收契约。当前 v0.7.4 修正了团队账号的身份清点，见 [交付说明](v0.7.4交付说明.md)；下列真实业务与外部环境事实仍需按实填写。

本清单把“代码通过测试”“部署配置完整”“真实产品与 Credits 已验收”分开记录。不能因本机测试或演示成功，就把真实体验、真实发放标记为完成。

## 离线验收工具

接口：`worker.acceptance.audit_readiness(store, service_config=None, credits_config=None, agent_config=None)`。

返回可序列化的 JSON 对象；调用已有 doctor，并只读检查数据库。它不发网络请求、不启动 Docker、不运行 shell、不改业务数据，也不触达作者或 Credits 系统。报告不输出账户邮箱、原始凭证、凭证摘要或原始体验内容。

0.7.4 起，身份检查合并启用的 Token 身份与 `accounts` 表中的活跃成员，仅读取账号 ID 与角色。不读取密码哈希或尝试登录。停用账号不计入；账号与 Token actor 冲突、无效角色及人类账号包含 Agent 角色会明确阻断配置就绪。一个账号拥有多个角色不能冒充多个独立主体；管理员角色也不自动算作已经完成职责分配。输出区分 `enabled_token_identity_count` 与 `enabled_account_identity_count`，不输出成员姓名、账号名或 ID。

本检查证明的是身份配置结构，不能证明密码有效、账号背后是不同真人、团队已履职或外部系统已经连通。`doctor.github.token_configured` 只描述执行该检查的进程环境，不能代替常驻采集器的认证日志与实际请求证据。

主要字段：

| 字段 | 含义 |
| --- | --- |
| `local_configuration_ready` | 本地静态配置、数据库完整性、队列健康和数据污染检查均通过 |
| `external_evidence_recorded` | 各条外部验收路径存在符合结构和关联要求的数据库记录 |
| `production_verified` | 本离线工具始终返回 false；数据库记录不能证明外部事实 |
| `checks` | 分 configuration、local_data、external_evidence 三层，包含状态、说明、数量及记录 ID |
| `warnings` | 离线证据局限和需要部署/人工验收的事项 |
| `doctor` | 当前无密钥的本机诊断结果 |

顶层状态：

- `blocked`：本地配置、数据库健康或测试数据隔离存在缺项。
- `configuration_ready_evidence_missing`：静态配置就绪，缺少真实运行应当产生的记录。
- `evidence_recorded_external_verification_required`：记录齐备，仍需要独立复核实物证据及外部系统日志。

外部证据状态 `recorded_unverified` 只表示“数据库中记录过”，不能显示成“已验证”。未找到记录时为 `missing`。

## 已具备的本机自动验收

运行：`python -m unittest discover -s tests -p test_acceptance.py -v`。

本测试包含真实 localhost HTTP 请求，使用各自独立的操作者、审核者、Agent 执行者、审批者、发放者身份完成：

1. 一轮前禁止联系；操作者不能伪造 actor，Agent 不能提交审核。
2. 审核者签署一轮，分别创建人与 Agent 体验。
3. 人工结果记录、Agent 领取任务/绑定结果；错误 run_id 和非 Agent 身份提交被拒绝。
4. 未签二轮仍禁止联系；二轮通过后才能创建联系草稿和记录回复。
5. 操作者记录访谈，审批者批准；普通操作者无法批准，审批者无法调用发放接口。
6. 发放者创建邀请，同一幂等键不重复创建；邀请未激活时不能记到账。
7. 内存假服务模拟激活后，核对生成台账和唯一复盘；复盘结束关闭该赞助。
8. 离线验收工具识别此数据库中的 synthetic/fixture 数据，拒绝把上述流程作为真实产品或真实发放验收。

这里的 HTTP 是真实本机传输，但产品数据、联系记录、访谈、Credits 提供方均为明确的合成测试。测试不会向作者发信，不会产生真实 Credits。

## 正式部署验收

| 检查项 | 必须取得的证据 | 验收责任 |
| --- | --- | --- |
| 独立生产数据库 | 无演示来源、synthetic/fixture 内容；完整性通过；路径与备份策略明确 | 运维/质控 |
| 身份隔离 | 至少审核、运营、审批、发放、Agent 五个独立主体；Agent 无审核或财务权限；凭证不进入前端持久化存储或仓库 | 管理员/质控 |
| 认证与会话 | 实际浏览器登录、退出、会话失效、越权、CSRF、幂等重放均有复现记录 | 质控 |
| TLS 与访问边界 | 生产访问使用有效 TLS；不向公网裸露本地明文接口 | 运维 |
| 采集路径 | 正式 GitHub 查询、任务完成、当前完整快照；仓库 ID/URL/SHA 和来源匹配；失败任务可定位 | 技术负责人 |
| 人用产品路径 | 团队按明确成功标准完成真实任务；保存步骤、输出、截图/录像、失败情况；审核者签署 | 体验负责人 |
| Agent 产品路径 | 自有 Agent 对指定 SHA 完成真实任务；任务/租约/身份和产物对应；由审核者查验产物 | Agent 负责人 |
| Docker 执行节点（若采用） | 审核固定 digest 镜像；对应 SHA 源码/依赖已准备；专用输出卷硬配额；超时回收实际有效 | 运维/Agent 负责人 |
| 两轮审核 | 两轮均在有效期内，绑定当前 SHA，二轮引用实际体验记录；缺项阻断联系 | 审核负责人 |
| 联系与访谈 | 获授权联系后按实际事实记录；作者身份、真实需求与领取账户得到确认 | 运营负责人 |
| Credits 联调 | 专用 PAT、正式活动、金额/账户/活动到期一致；单独审批者和发放者；服务端邀请/激活/参与者记录逐项核对 | 审批/发放负责人 |
| Credits 异常 | 超时后的 unknown 状态有核对步骤，不能重复提交；重复核对不重复台账 | 发放负责人/质控 |
| 复盘闭环 | 到期任务、真实用量依据、阶段成果和后续决定均落库 | 运营/计划负责人 |
| 备份恢复 | 从备份恢复到独立目录后读表、审核/台账数量一致，恢复过程留记录 | 运维 |

## 数据与判断边界

工具会检查项目来源、业务表中的明确 synthetic/fixture/模拟标记和无效示例域名；README 中讨论 demo 或测试 fixture 不会自动把真实项目标记成演示库。标记检测仍是启发式检查，异常命中需要人工核对，未命中也不等于真实性证明。

采集验收要求当前、完整、有匹配仓库 ID/SHA 和 GitHub API 来源的快照。体验验收要求成功结果包含步骤和产物；Agent 还要求已完成租约和服务端记录的执行者。两轮审核必须引用这些符合条件的体验。Credits 验收要求已激活参与者、邀请、活动、审批账户/额度、提供方和独立核对责任人关联一致。

即便上述字段全部吻合，本地数据库持有者仍可伪造记录。因此上线签署必须核验真实截图/日志/文件和提供方审计记录，而不是只看离线 JSON 的数量。

最后的上线记录应包含：版本、验收时间、数据库/部署标识、执行人员、通过与失败项、证据存放位置、未完成项及负责人。外部环境或凭证未提供时，应记录为未完成，不能代填通过。
