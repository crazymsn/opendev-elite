# OpenDev Elite 项目入选与排除标准

标准版本：`sop-2026-09-v3`。本标准适用于全球项目，目的是决定是否值得进入评测以及何时暂停或停止推进。入选、两轮通过和获得赞助是三个不同结论。

## 一、支持范围

### 1. 面向开发者

AI 编程、调试、评测、数据处理、RAG、模型路由与推理等；说明具体开发任务和产出。

### 2. 面向真实用户

帮助用户完成研究、创作、办公、学习或业务任务的 AI 工具；有清楚的输入、结果和使用边界。

### 3. 支撑 Agent 运行

运行时、编排、记忆、工具调用、观测、评测、身份及隔离等；有具体下游工作流。

### 4. 供 Agent 实际调用

通过 API、CLI、SDK 或协议提供可执行能力；检查机器可读输入输出、错误语义、权限与调用成本。

## 二、入选前提：六项均须有依据

### 1. 明确的人、任务与结果

写清谁在什么场景下遇到什么问题、现有做法哪里不足、工具如何产生可核对结果。个人自用也有效；不强求付费用户或规模。

### 2. AI 能力与场景适配

核心工作流确实服务 AI 使用、开发或 Agent；名称含 AI、添加聊天框或追热点本身不构成依据。

### 3. 存在可核对的核心路径

提供核心实现、可用版本、安装入口或调用示例及预期输出。早期原型可入选；仅承诺未来能力先暂缓。此步检查入口，实际成功由后续体验验证。

### 4. 有意义的持续维护

入选至少引用过去 365 天内两个不同日期的功能/修复提交、实质发布或维护者对具体问题的响应，并提供至少两个不同的对应来源。主要维护事实日期须包含在该日期列表中。仅更新时间、机器人依赖更新、格式改动、刷提交或空发布不能单独证明维护。

### 5. 可评测、可追溯且无已确认排除项

核对代码/服务入口、作者关系、许可及第三方依赖、数据与凭证处理、执行权限和成本边界。可在可接受条件下评测；关键事实不清先暂缓，不把公开仓库自动当作可任意使用。

### 6. 达到不可互相抵消的质量门槛

五项分别评 0–4 分，按权重折算为百分制。**总分至少 80/100，每项至少 3/4 分**，并满足维护日期、来源、权限与排除检查，才允许入选。全部 3 分只有 75 分，应先暂缓。高总分不能抵消某项 0–2 分或已确认排除条件。

| 维度 | 权重 | 3 分必须具备 | 4 分额外依据 |
| --- | --- | --- | --- |
| 真实需求与任务价值 | 20% | 明确用户、重复任务、现有流程痛点及具体使用或需求来源 | 多个独立场景或可量化收益，不要求付费用户 |
| 工程成熟度 | 25% | 已交付核心实现、清晰模块职责、关键路径测试或可复核验证、失败处理 | 负例、回归及可靠性证据；存在 tests 目录不算通过 |
| 维护连续性与响应 | 20% | 一年内两个不同日期的实质维护及两个对应来源，解释解决的问题 | 持续交付，用户反馈进入迭代 |
| 差异化与新增贡献 | 20% | 至少一个具名替代方案、可核对新增能力或工作流改善及限制 | 多个对照或复用案例支持明显优势 |
| 可评测性与使用边界 | 15% | 固定版本步骤、输入输出、失败用例、预算和权限边界；Agent 工具须有调用契约与错误语义 | 可复现基准与结果校验；不代表团队已完成体验 |

0 分表示没有可核查依据；1 分只有声明或零散材料；2 分基本可用但关键证据不足；3 分达到该维度质量要求；4 分有更强验证与明确优势。缺失评分保持未评，不自动补成合格分数。

计算公式：`总分 = Σ(该项评分 ÷ 4 × 该项权重)`。例如需求 4 分、其余 3 分恰为 80；可评测性 2 分、其余 4 分虽然 92.5，仍不能入选。每项都必须有事实说明与来源，评分人对核查负责，系统不凭文本长度、关键词、Stars 或模型自报分自动录取。

## 三、持续维护的判定

### 1. 看变化内容，不数绿色格子

优先记录具体变更解决了什么问题、谁回应、何时回应及来源。提交数、最近推送和 Stars 仅用于发现线索。

### 2. 90 天观察，必要时回看一年

90 天是建议检索窗口，不是淘汰线；结合近 6–12 个月发布节奏、依赖适配和公开响应。没有近期提交不等于弃用。

### 3. 成熟稳定与早期密集开发分别判断

成熟项目可由实质修复、兼容性发布或具体维护响应证明维护；新项目看已交付的最小闭环与后续动作，不因历史短或单人维护而淘汰。

### 4. 信息不足先暂缓

公开响应不足、休假或节奏变化先记录待核查事项；不得为补证据绕过两轮筛选联系作者。明确归档、弃用声明或长期不可用且无修复依据，才支持停止维护结论。

## 四、暂缓条件

### 1. 关键资料不足

真实场景、源码、来源或判断依据不足；列出要补的具体材料。

记录条款：`evidence_missing`。

### 2. 维护情况待确认

只有更新时间、机械提交，或无法判断项目是否仍受支持。

记录条款：`maintenance_uncertain`。

### 3. 核心能力尚待交付

只有路线图、等待开放测试或核心流程未形成；写明重新评估触发条件。

记录条款：`not_ready`。

### 4. 评测条件暂不具备

缺少匹配硬件、测试账号、预算或环境；环境失败不等同于产品无效。

记录条款：`evaluation_blocked`。

### 5. 归属或使用权限待核对

许可证缺失、依赖条款不清、作者关系或可评测权限待确认。

记录条款：`rights_uncertain`。

### 6. 重要风险需要验证

高权限操作、数据外发、成本或结果可靠性缺少说明；先验证，不能凭猜测指控。

记录条款：`risk_unresolved`。

### 7. 质量评分尚未达到门槛

总分不足 80 或任一维度低于 3 分时使用 `quality_below_threshold`。写清待改进维度及复评所需证据；不能为提高通过率抬分。

### 8. 只有一次实质维护

只有初始化、一次发布或一个日期的维护事实时使用 `maintenance_single_event`。保留候选，等待后续实质维护，不要求先积累 Stars。

## 五、排除条件

### 1. 与目标场景无关

核心能力不服务真实 AI/Agent 使用或开发，且不能说明可信的相关场景。

记录条款：`outside_scope`。

### 2. 只有内容，没有工具能力

仅链接汇总、教程搬运、论文目录、静态提示词或宣传页面，没有可执行产品/工具路径。资料中附带可复用工具时应单独评估工具。

记录条款：`content_only`。

### 3. 已确认停止维护

维护者明确弃用、仓库归档且无接续版本，或核心能力长期不可用且有停止支持的依据。低频更新本身不满足本条。

记录条款：`abandoned`。

### 4. 搬运且无可核对新增贡献

经对比确认只是镜像、改名、套壳或复制宣传，没有实质工程/场景贡献。Fork、模型 API 封装和成熟方案组合本身不排除。

记录条款：`duplicate_no_contribution`。

### 5. 实际验证后不成立

在匹配环境和合理复测后，核心任务无法完成，或相对现有方案没有可说明的收益。必须记录样本、对照和局限，不能只凭主观印象。

记录条款：`no_real_value`。

### 6. 已证实的严重不诚信或恶意行为

有可复核证据证明冒用身份、伪造关键产品证据、窃取凭证或以欺骗/未经授权操作为核心用途。争议、传闻或一条告警不足以定性。

记录条款：`proven_misconduct`。

### 7. 已确认无法开展评测或支持

有明确来源证明相关代码、服务或依赖无可用的评测/使用权限且无法解决。缺少许可证或商业条款本身先暂缓核对。

记录条款：`rights_blocked`。

### 8. 严重风险无法接受或缓解

实际核查发现不可接受的数据泄露、破坏性执行、权限或费用风险，且当前无法隔离、约束或修复；保留复现及版本依据。

记录条款：`unmitigated_risk`。

## 六、通过门槛后的优先级

### 1. 可衡量的用户收益

真实任务完成率、时间、质量、可访问性或成本改善；小众高价值问题同样值得关注。

### 2. 可说明的差异与工程贡献

比对具体替代方案，关注集成深度、稳定性、部署体验或新的工作流，而非只要求自研模型。

### 3. 持续交付与开放协作

对问题负责、反馈进入迭代、边界透明；不强求庞大团队、固定发布频率或全英文文档。

### 4. 赞助能解除明确瓶颈

访谈后说明 Credits 用于何种开发/评测、为何适合、如何衡量里程碑及后续成本；不靠强制宣传或采集隐私换取支持。

## 七、证据与公平原则

1. 每条判断记录责任人、当前版本、观察日期、来源、事实与推断的区别。外部链接与截图不等于已复现。

2. 入选只表示可以投入评测；技术通过、产品通过与赞助决定分别留痕。优先级不能抵消排除条件。

3. 排除须有对应条款和证据，记录纠正后可重评的条件；资料不足使用暂缓，禁止把未知写成不合格。

4. 不以 Stars、国籍、地域、融资、团队人数、商业模式、项目新旧或是否封装现有模型单独决定。

## 八、典型边界如何处理

| 情况 | 处理 |
| --- | --- |
| 单人、零 Stars、新项目，有真实任务、核心入口、实质维护及必要权限依据 | 满足五项评分及两个维护日期后可入选，不要求先有付费用户 |
| 面向普通用户的 AI 办公/创作工具，有明确任务和可评测入口 | 属于支持范围，不必是开发者工具 |
| 供 Agent 调用的程序，没有图形界面 | 达到质量门槛后可以入选；后续检查调用语义、结构化结果、失败反馈、权限与成本 |
| 成熟项目几个月没有提交，但有具体支持响应与持续可用依据 | 结合完整维护节奏判断，不因超过 90 天直接淘汰 |
| 连续机器人提交或只刷新 README 日期 | 不能单独确认持续维护；缺少其他证据先暂缓 |
| 封装模型 API 或 Fork 已有项目，但改善了真实工作流 | 不自动排除；在第二轮比较新增价值、稳定性和使用成本 |
| 经对比只是镜像、改名或复制宣传，没有新增贡献 | 按无实质贡献排除，记录对照来源 |
| 没有 LICENSE、条款不清或需商业授权 | 先核对权限，暂缓；不自动定性为侵权或恶意 |
| 缺 GPU、账号或预算导致测试失败 | 暂缓评测，不能由此判断产品没有价值 |
| 合适环境下完成真实体验后核心任务失败，合理复测仍不能成立 | 记录第二轮未通过、关联体验与比较依据，再考虑产品价值排除 |
| 只有演示视频、营销页或未来路线图 | 尚无可用核心能力先暂缓；确认只是内容/宣传而无工具路径时排除 |

## 九、团队执行顺序

1. 采集公开资料并分配负责人和受众。检索信号只负责排序与发现。
2. 填写方向、用户任务、核心入口、具名替代方案、评测计划、归属/权限/风险核查、维护信号及两个日期，并逐维度评分、引用来源和说明理由。任何未知保留为未知。
3. 入选需六项前提具备依据、总分至少 80 且每项至少 3 分、维护日期及来源合格，并没有已确认排除项；暂缓或排除记录对应条款与重评触发条件。
4. 第一轮检查核心实现、工程质量、有效维护、文档和仓库规范，强度与项目规模相称。
5. 第二轮按真实任务验证问题、使用表现、差异化及潜力。人用工具由团队体验；Agent 工具由自有 Agent 执行；混合产品覆盖两类受众。记录成功与失败样本、延迟/成本及权限行为，不能只展示最佳结果。
6. 前两轮当前有效通过后才联系；访谈后判断工程师/创业者画像、支持意愿、Credits 适配、具体瓶颈和可核对里程碑。入选优先级不直接决定额度。
7. 由独立执行人处理已批准的 Credits，核对到账并按期复盘。版本、受众、标准变化或审核过期须重评；历史不覆盖。

## 十、系统落实与能力边界

工作台“入选标准”与“项目入选评估”从同一标准目录加载。服务端检查条款与结论一致、实质维护信号、过去一年内两个不同日期与至少两个维护来源，以及五项整数评分、事实说明和来源；总分由服务端重算，不接受客户端自报总分。停止维护和范围外排除还需与相应事实状态一致。

“实际验证后不成立”排除要求当前版本的第二轮未通过记录，并关联至少一份当前版本、已完成的产品体验。环境失败不足以满足这条排除。服务端只能检查证据结构、版本和关联关系，不能自动证明描述的事实为真；审核人仍须实际核查。

90 天是建议检索窗口，并非淘汰线；v3 入选明确要求过去 365 天内两个不同日期的实质维护事实。超过一年未取得维护依据应暂缓，不自动判为弃用。入选评估原有 30 天有效期仍保留，它约束团队判断的新鲜度，与“代码多久必须提交一次”不同。

新标准不会自动排除现有候选或生成审核结论。旧标准评估会标为需重评，已发生的 Credits 对账和到账后的复盘继续保留。

开发接入见 [档案与流程接口](v0.6档案与流程接口.md)。本轮软件更新和测试记录见 [v0.8.0 交付说明](v0.8.0交付说明.md)。

0.7.0 工作台进一步把分配、证据采集、入选评估和第一轮技术复核接入团队待办，按同一套当前条件生成任务。开发者与团队档案汇总跨项目资料与访谈来源，保持候选关系、真实确认和画像判断的区别。新增接口、权限与验证见 [v0.7.0 交付说明](v0.7.0交付说明.md)。

## 十一、把标准用于一次真实评估

以下问题用于给 v3 的五项评分收集依据。先满足总分、单项底线和对应阶段前提，再讨论优先级；不能用总分掩盖核心任务失败，也不能因缺一项资料直接排除。

| 判断项 | 必须回答的问题 | 合适的证据 | 不足时的处理 |
| --- | --- | --- | --- |
| 真实场景 | 谁或哪个 Agent，在什么条件下，完成什么任务？ | 具体输入、预期产出、原有流程；第一轮可先记录可核查入口 | 暂缓补充任务描述，不把营销口号当需求 |
| 工程实现 | 从入口到结果经过哪些关键模块？失败如何处理？ | 同一提交版本的入口、实际执行链、异常与权限处理；按需扩展代码阅读 | 自动样本未覆盖核心路径时补采，不因语言或目录命名扣分 |
| 维护责任 | 最近一次实质变化解决了什么问题？ | 提交 diff、发布内容或维护者的具体响应，附日期与链接 | 一次初始提交或仅版本号变化不能证明持续性，保留观察 |
| 实际可用 | 在预先约定的条件下，任务能否重复完成？ | 团队或自有 Agent 的输入、原始结果、环境、版本、失败记录 | 区分环境、产品和测试设计问题，合理复测 |
| Agent 适配 | Agent 能否理解、调用、校验和处理失败？ | 调用契约、结构化结果、错误语义、超时取消、重试副作用、权限与成本表现 | 不以“支持 MCP/API”代替任务成功；只验证产品声明覆盖的能力 |
| 差异与收益 | 比当前替代方案具体改善了什么？代价是什么？ | 同一任务和资源条件下的完成率、质量、耗时、成本及限制 | 没有显著性能优势时也可检查工作流、可部署性或小众需求收益 |
| 交付潜力 | 反馈能否转化为下一次可核查交付？ | 历史问题到修复的链路、明确的下一阶段目标 | 不把路线图写成已交付能力，也不要求已有商业规模 |
| 赞助适配 | Credits 是否能解除当前瓶颈，怎样检查结果？ | 访谈后的具体用途、预算、里程碑、负责人和复盘日期 | 项目优秀但 Credits 不适配时记录本轮不支持，不倒推项目不合格 |

评估中明确标注三种状态：**仓库声明、已查看的实现证据、实际运行结果**。例如，有测试文件不代表测试通过；CI 配置存在不代表当前提交的 CI 成功；隔离了依赖不代表隔离了不可信代码；模型模板检查通过不代表真实推理服务器可用。

采集器从 0.7.1 起默认发现包含 Fork 的候选，并按实现、测试、依赖声明、CI 四类提供至多六个文件样本。样本选择是有上限的路径启发式，不能替代上述复核。仍需核对 Fork 相对上游的新增贡献，补读大文件、被截断目录树和未覆盖的核心模块。参见 [真实候选技术复核准备](真实候选技术复核准备-20260908.md)。

## 十二、接口新增字段与升级

`evidence.quality` 包含 `problem`、`engineering`、`maintenance`、`differentiation`、`evaluability` 五个对象；每个对象需 `score`（0–4 的整数）和非空 `sources` 列表。维护维度至少两个不同来源。新增 `evidence.differentiation`、`evidence.evaluation_plan` 文本，以及 `evidence.maintenance_dates` 日期列表（YYYY-MM-DD）。保留原 `evidence.maintenance_date` 作为主要事实日期。

`/api/projects/{id}` 的 `qualification.quality` 返回服务端推导的总分、各项分值、证据完整性、门槛与是否达标；旧政策记录不补造分数。记录继续绑定当前 SHA、受众、评估人和时间。旧 v2 入选记录自动标为需重评，不能沿用旧分进入技术复核、联系或赞助；候选与历史记录保留。已发生的财务对账与复盘仍可继续。
