# v0.7.2 技术证据阅读规格

第一轮要求审核核心实现、维护和仓库规范。0.7.1 已采集相关内容，但负责人需要阅读原始 JSON。此次在项目的“仓库档案”中，把技术快照呈现为可展开的文件、提交、发布和议题材料；原始记录仍可展开核查。

## 范围与边界

- 服务端从同一已采集快照生成只读投影，不发起网络请求、不执行代码、不修改入选或评审。
- 展示采集 SHA、日期、是否匹配当前已知版本、许可标识、Fork 上游以及采集缺项；目录截断明确显示。
- 至多六份代码预览，最多每份 300 行及 12,000 字符。只解码上限内的 UTF-8 文本；二进制、无效编码、缺内容和 SHA 不一致分别展示状态。Git blob SHA 按原始字节核对，预览截断不影响校验。
- 文件链接使用采集时的仓库名和提交 SHA；历史重命名不把旧快照链接到新内容。历史样本没有角色或完整 SHA 依据时如实显示。
- 提交最多 20 条，发布最多 10 条，Issue/PR 最多 15 条；分别显示采集数、展示数、来源有无后续分页。未采集与成功返回空列表不同。
- Issue 更新时间不冒充维护者回应；提交标题不冒充实质改动审查；发布与议题记录不保证对应该提交的能力。
- 前后端保持现有权限：人类工作台角色可读，匿名和 Agent 身份不可读项目接口。沿用现有路由与退出状态清理。

## 界面

使用现有暖白底、深绿强调、浅色边框、12px 卡片圆角及系统内的正文/等宽字体。与现有“仓库档案”组合，采用原生 details 键盘展开，代码在独立区域滚动；不引入 CDN、依赖或额外站点导航。

外部文件、提交说明和发布说明作为文本呈现，不渲染 HTML、图片或执行脚本。保留明确的来源跳转，不自动打开第三方页面。

## 验收

| 要求 | 证据 |
| --- | --- |
| 版本、重命名来源、缺项与历史数据兼容 | test_technical_evidence.py |
| 解码上限、字节 SHA、文本截断与异常状态 | test_technical_evidence.py |
| 私有工作台访问边界、查询无评估写入 | 项目 API 权限测试 |
| 中英文、键盘、四种宽度、被动显示外部代码、退出清理 | browser-v072-technical.js，独立合成库 |
| 三个真实仓库的投影可读且无业务写入 | 固定版本采集库和正式浏览器检查 |
| 无既有流程回归、独立安装资源与部署保持 | 完整回归、wheel-smoke.py、备份与升级验证 |

本功能只改善技术复核的材料获取。团队仍须实际阅读并判断；第二轮仍须团队或自有 Agent 真实体验，不能把证据页作为已评测结果。
